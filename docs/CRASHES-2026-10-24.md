## 1. The in-game crash: a destroyed texture view in a draw job

### What happened
- **When:** 15:12:44 local, 14 minutes into the session, in the Lobby, on PreyVR-70 (DLL `76151F0A…`).
- **Where:** `JobSystem_Worker_6`, an access violation reading address `0x80` in
  `d3d11.dll+0x1BCFD`. That instruction is `mov rax,[rdx+80h]` with `rdx = 0`, in a
  small d3d11 accessor.
- **PreyVR's log:** it ends at 15:12:59. Its own worker thread is not one the crash handler suspends, so it kept logging.

The stack, as PreyDll RVAs (PreyDll at `0x7FF81F2A0000`):

| 13–16 | d3d11 | | `PSSetShaderResources` internals |
| 12 | `0xF63CF8` | `FUN_180F63C70` | binds one view per stage, through a per-slot cache: VS `vt+0xC8`, **PS `vt+0x40`** (this call, at `0xF63CF5`), GS `+0xF8`, DS `+0x1F8`, HS `+0x1D8` |

**It is not the cull-camera crash.** That one faults at `0x27EC40` under the
render-content job `0x27F820`. The cull watch's last summary, 8 s before this
crash, read `staleItems=0 doomedItems=0`.

### What was bound
- **The view bound:** `0x26BD7820A28`, from the worker's own stack (`FUN_180F63C70`'s `[rsp+0x40]`). Its d3d11 vtables are intact, but the internal block d3d11 reads through it (`0x26BD30DC088`) is all zeros. That is a destroyed view, or one never initialised.
- **The entry it came from:** the faulting call was slot 2 (`rdi = 2`). The entry being applied, `0x26AE6E79500` in resource set `0x26B5DFC8E00` (15 entries), is slot 2. **In the dump it holds a different view, `0x26C6AD6D0A8`.** No entry in the set holds the bound one.
- **The set's other entries:** slots 0 to 2 hold three views at neighbouring addresses (`0x26C6AD970A8`, `0x26C6AD9A1A8`, `0x26C6AD6D0A8`). Slots 3 to 14 hold three shared views, which look like default textures.
- **So the entry was rewritten between the worker reading it and the dump.** The new views were most likely made together: a material's first three textures, given new views at once.

### How a set's entries are written (observed static)
- **The rebuild:** `FUN_180F63F10` (the set's vtable `0x1DD1D38`, slot `+0x10`).
  - It sets the count (`+0x80`) to 0, then re-appends every entry into the same array through `FUN_180F63840`.
  - Each texture's view comes from `FUN_18100CE90`.
  - The array is reallocated only when it outgrows its capacity, which frees the old array.
- **No double buffering:** a rebuild rewrites the live array in place.
- **The draw path only reads:** `FUN_180F00E00` caches the set per slot, then `FUN_180F66720` and `FUN_180F63C70` read the entries. Nothing on it rebuilds.
- **Inference:** a rebuild on another thread overlapped this draw job, after the texture had released its old view. A rebuild that grows the array would be a second way to crash: the reader would walk freed memory.

### Who was running (observed, from all 104 threads)
- **The render thread (20)** was in `RT_RenderScene` (`0xF41CA0`), called from PreyVR's DualSceneStereo detour. It was waiting in `0xED9D70` for these draw jobs.
  - **This was the first submission of a doubled frame:** the detour stores `gStep = 2` (`first_submission`) just before the call, and `3` (`between`) just after it.
  - The first submission is the engine's own pass, with the eye camera. Its teardown is deferred to the second submission.
- **The main thread (0)** was waiting for the render thread (`0xFEF6A1`, pumping messages).
- **Every other engine worker was idle.** No thread was in texture or resource-set code when the dump was written.
- **So the writer was neither the render thread nor the main thread.** A job worker or a streaming thread is likely (inference). Texture streaming would fit the three fresh views.

### PreyVR's part (inference only, not established)
- **Not on the faulting stack.** The UI batch's changes (the command channel and HudLayer) are not on any of these paths.
- **Doubled rendering may widen the window.** It doubles the time draw jobs run in each frame, and a VR resolution (2644×2644 per eye) with two eye cameras keeps texture streaming busy. Both would widen a race the engine already has. Whether flat Prey hits it is unknown.

### What can be done
1. **Find the writer first (recommended).**
   - Add a read-only hook on `FUN_180F63F10`, in the style of the cull watch. Per rebuild, it notes the thread and the caller's return address (as an RVA), and whether a scene pass is in flight (DualSceneStereo's `gStep` is not idle).
   - It counts the rebuilds that overlap a pass, and logs the first few with their callers.
   - One headset session then says whether overlapping rebuilds are routine (in which case this crash is a matter of time), which code makes them, and on which thread.
2. **Then fix at the writer.** Defer a rebuild requested off the render thread during a pass until the pass ends, or serialise it with the draw jobs. The design depends on step 1.
3. **A stopgap, not recommended first:** an SEH guard around the bind in `FUN_180F63C70`, which would skip a binding that faults. It would turn this exact crash into one draw with a missing texture for a frame. But:
   - it detours a function that runs for every resource of every draw;
   - it only catches a view whose internals were zeroed, while a reused allocation would bind garbage silently;
   - leaving d3d11 mid-call is only safe if the call faulted before it changed any state.

## 2. The quit crash: XR teardown in PreyVR's global destructors

**Seven of today's eight Windows dumps** (10:16 to 14:21) share one stack:
- Prey's `main` returns, then `ExitProcess`, then `LdrShutdownProcess` unloads PreyVR.
- The C runtime destroys PreyVR's globals (about ten PreyVR frames).
- A destructor calls `xrDestroySwapchain`. SteamVR's `vrclient_x64` raises an exception inside it, because its threads have already been ended.
- The OpenXR loader then fails fast: `c0000409`, `FAST_FAIL_FATAL_APP_EXIT`.

**The eighth** (13:49, run `player-20261024-134631`) also starts from
`LdrShutdownProcess`. It fails fast inside PreyVR itself, in a different
destructor that aborts; a joinable `std::thread` is one way to get that.

**The likely owner** is `gHost` (XrSessionLifecycle.cpp). Its `std::unique_ptr<LayerSwapchain>` members destroy their swapchains when it is destroyed, and PreyVR's `DllMain` does nothing on detach.

**Impact:** the game's own work is finished by then. Each quit leaves a 50 MB dump in `%LOCALAPPDATA%\CrashDumps` (about 400 MB today) and a Windows error report.

**Fix (small; not done):**
- Make no OpenXR, D3D or thread calls from global destructors at process exit. Either let the owners skip them when `DllMain` reports `DLL_PROCESS_DETACH` for process termination (`reserved != nullptr`), or never destroy `gHost`; the OS reclaims everything.
- Audit the other globals whose destructors touch XR, D3D or threads; the 13:49 variant shows at least one more.
- Build a PDB for each packaged DLL, kept beside the build and not shipped. Today the PreyVR frames could only be matched by disassembly.

## Done 2026-10-24 (PreyVR-71)

### The rebuild watch (`src/dll/ResourceSetWatch.{h,cpp}`)
- **What it hooks:** a read-only hook on `FUN_180F63F10`. It installs only on the exact prologue (48 bytes, up to the count reset), and only if the vtable slot `0x1DD1D48` still points at it. It is the function's one reference; `0x2CF43B8` is its `.pdata` record.
- **When it runs:** it is installed by the command worker once PreyDll is pinned, VR or not. `PREYVR_RSET_WATCH=0` leaves it out; `rset.watch 0|1` pauses and resumes it; `rset.report` reads it.
- **What it records for each rebuild:**
  - the thread: `render` (the thread that runs the scene submissions), `main` (the input drain's) or `other`;
  - whether a top-level submission was in flight when it started or ended (`CurrentSceneSubmission`, new in DualSceneStereo and set by `SceneProbe`, so every path through the detour counts);
  - whether the entry array moved;
  - its caller, in a table of the first 16 callers.
- **What it logs** (`preyvr_resource_set`):
  - `detail=new_caller`, once per caller;
  - `detail=race`: a rebuild by any thread but the render thread during a submission. It gives the step, the entry count, whether the array grew, and the caller with five more frames of its stack as PreyDll RVAs. The first 32 are logged, then one in 256.
  - `summary`, every 60 s.
- **How to read it:**
  - `races=0` all session, with the summary's `callers=` showing who rebuilds: they are serialised with the passes, and the 10-24 crash needs another explanation.
  - `races>0`: the `detail=race` lines name the writer's code path and thread, which is the fix's input.
  - Note that before VR starts, the render thread is not known yet, so its rebuilds count as `other` (never as races).

### The quit crash
**The owners:** `src/dll/NeverDestroyed.h` makes the globals that own XR handles, D3D objects or a thread on the heap, and never frees them:
- `gHost` (XrSessionState.h);
- ResearchHotkeys' `gThread` (the 13:49 abort: joinable at exit, so `std::terminate`);
- DebugOverlay's `gRenderer`;
- HudLayer's `captures`, `textPanels`, `parts`, `redrawDepth`, `inventoryRight` and `nativeWrist`.

**Why those four files:** they are linked after everything else. Globals are destroyed in reverse link order, so `gHost` went first, then `gThread`. HudLayer's and DebugOverlay's D3D releases had never run at exit. They would have run for the first time once the first two were fixed, under the loader lock.

**What still runs:** their runtime teardown (StopXrSession, the lanes' releases) is unchanged. Only the exit-time destructors are gone.

**The inventory:** the compiler's dynamic-atexit symbols (`??__F…`, from `dumpbin /symbols` on the DLL's objects) list every global destructor. 138 before; none of these nine now. The rest are mutexes, strings and containers of plain data, plus the log's stream, which closes the file.

**A PDB for every build:**
- `/Z7` on the DLL's objects, and `/DEBUG:FULL /OPT:REF /OPT:ICF` at link. `PreyVR.pdb` lands beside the DLL, and the DLL names it (RSDS `{67831E8F…}`).
- The package's copy is `build/packages/PreyVR-71-symbols/PreyVR.pdb`, kept outside the zip.

## Field result 2026-10-24 (PreyVR-71, run player-20261024-155349)
A 10-minute session from 15:53, with VR active from 15:54:51. No access violation this time.

### The quit crash: fixed (observed runtime)
- **The quit was like the crashing ones.** The XR session was still running at quit (no `torn_down`), and the last line is the quit's loading screen, exactly as in the two crashing runs `player-20261024-141603` and `-135843`.
- **Those wrote a dump within 5 s. This one wrote nothing:** no new `Prey.exe.*.dmp` in `%LOCALAPPDATA%\CrashDumps`, no new Windows error report, and the game's `error.log` is still the one from 15:12.

### The rebuild watch
- **The numbers:** 5,352,956 rebuilds in 9 minutes, about 10,000 a second, from **one call site, `0xF6F01F`**. `races=0`: no rebuild by any thread but the render thread during a submission.
- **Every rebuild was on the render thread (7892):**
  - 5,298,267 during a scene submission and 38,635 outside one;
  - the 16,054 counted as `other` were the same thread before VR started, when the watch did not know it yet (the caveat in Done).
- **The call site:** `0xF6F01F` is in `FUN_180F6EF50`, the engine's "update a resource set" step (observed static):
  - for each resource, `FUN_180F6DDD0` reads the texture's current view and flags a change;
  - it records the set in a global list (`FUN_180F74DA0` on `0x2B24DA0`);
  - then it **always** calls the rebuild (vtable `+0x10`), whether anything changed or not.
- **Its 16 callers** are spread over the renderer. One is `FUN_180F00850` (`0xF009DF`), the resource-binding function of F-016's `0xF00994` crash, which sits beside this crash's draw-item function `0xF00A90`.

### What this changes
- **The writer is the render thread itself (inference, now the leading one).**
  - The render thread prepares render items during the scene pass, rebuilding their sets in place every time, while draw jobs it has already launched read sets on the workers.
  - If a set shared by an item a worker is drawing is rebuilt with a texture's new view, after the texture has released the old one, the worker binds the destroyed view.
  - In the 10-24 dump the render thread was already waiting for the jobs. That fits a rewrite made just before it started waiting.
- **The race needs a view change at that moment** (texture streaming, for example). The rebuilds themselves happen about 10,000 times a second, so the crash is rare rather than constant.
- **Even without a view change** the in-place rewrite briefly zeroes the count. A reader that catches it skips that item's bindings for one draw: a glitch, not a crash.
- **Not established:** whether the rebuilds overlap running draw jobs. This watch's race rule left the render thread out.

### Next instrument (not built)
Count the draw jobs in flight (a read-only hook on the draw job `FUN_180ED9C70`, entry and exit). Count the render-thread rebuilds made while any are running. Of those, count the ones that **change a view pointer** in the set: the crash's exact precondition. Log their stacks, which name which of the 16 callers. If that count is not zero, the fix is a deferred release of the old views until the frame's draw jobs finish, or serialising those rebuilds with the jobs.
