# Controls: the Steam Frame's own layout, and duplicated bindings (2026-10-17)

TODO items "Rebind controls to be nicer on Steam Frame controllers" and "Fix duplicated
bindings". Phases 0 and 1 of a headset-agnostic input plan (below):
- **Phase 0:** the Frame's own buttons, and the cross-controller binding bugs found while
  auditing the input. Worn 2026-10-17 (package PreyVR-5): working as expected.
- **Phase 1** (below): named actions in three action sets, grab on the left trigger, and
  View closing menus. Worn 2026-10-17 (PreyVR-6): verified working.
- **Phase 2** (below): Prey's own gamepad buttons that VR lacked, the recenter chord
  on Menu, and a live dump of Prey's key bindings. Worn 2026-10-17 (PreyVR-7):
  verified, and the dump proved every binding it relied on.
- **Phase 3** (below): fingers follow the controller, and a Controls tab listing
  what each button does by the runtime's own names. **Offline-tested only; not yet
  worn.**

## What was wrong

**The Frame profile was SteamVR's Touch emulation, copied.** The 10-13 profile
(`VR-OPTIONS-IMGUI-2026-10-13.md`, step 4) kept "what that emulation gave every role", so
it inherited the emulation's folds (`frame_controller_remapping.json` in SteamVR's
`drivers\frame_controller\resources\input`):

| Frame button | Bound to | Meant |
|---|---|---|
| Right X, Y and B | `menu_cancel` | crouch in play, back in menus: three buttons for one |
| Left D-pad down | `menu_accept` + `navigate_down` | the TranScribe in play, Prey's X in menus |
| Left D-pad up / left / right | `menu_cancel` + `navigate_*` | Prey's Y in menus; the recenter chord's Y |
| Left View and right Menu | `menu_start` | both pause |
| Bumpers, left stick click, every `/touch` | nothing | |

So when Prey's inventory prompt said "X: Equip", the Frame's X backed out of the screen.
SteamVR's record of what it bound, `C:\Program Files (x86)\Steam\config\openxr\
steam.app.480490_frame_controller_2_binding.json`, shows exactly this table. The 10-17
headset logs accepted the first of the eight fallback sets (`menu=view_and_menu,
right_xy_as_b`).

**The Frame paths were guesses.** The comment said every path was checked against the
bundled `xr.xml`. Nothing checked them, and OpenXR SDK 1.1.60's registry has no Frame
profile at all. Hence eight fallback sets guessing where Menu was. Valve's list
([Steam Frame Input](https://partner.steamgames.com/doc/steamhardware/steamframe/input))
settles it:
- Right hand: A, B, X, Y, Menu, bumper.
- Left hand: D-pad, View, bumper.
- Both hands: system, trigger, squeeze, thumbstick, and `touch` on every one of them.

**The profile was renamed.** Valve documents `/interaction_profiles/valve/
frame_controller_valve` from SteamVR 2.15.1. The mod suggested only the older
`frame_controller`. Today's SteamVR still accepts that name (`vrclient_x64.dll` holds
both strings, and the runtime reports `frame_controller` as active), but nothing
promises it will keep doing so.

**Bugs on every controller:**
- **C1: the recenter chord used and reloaded.** Its first grip went through the use
  button before Y completed the chord: the left grip used the selected target, the
  right grip reloaded and, held long enough, holstered the weapon. Only the second grip
  was refused (`InteractionUse.cpp`, "both grips in the same frame"). The player guide
  said the chord never uses anything.
- **C2: VR Options changed tabs on grip press**, with no chord suppression. Each grip of
  the chord flipped a tab and then flipped it back. Game menus already changed tabs on
  release, with suppression.
- **C3: Y before the grips sent Prey's Y action** in game menus, then recentered.
- **No hysteresis on trigger and grip.** They pressed at 0.5 and 0.55 and released at
  the same values. The sticks already had hysteresis.
- **The controls card named Touch's left menu button**, which the Frame does not have.

## What changed

**Roles** (`preyvr/ControllerProfiles.h`):
- `accept` and `cancel` are now A and B on the right on every controller, bound in the
  shared set.
- New: `secondary` (Prey's X action in menus), `tertiary` (Prey's Y action; the recenter
  chord's button) and `inventory` (the TranScribe in play).
- On Touch and Index, the X button (Index: left A) carries both `secondary` and
  `inventory`. It already did both jobs; now each context reads its own role. Touch and
  Index behave exactly as before.

**The Frame** is a gamepad split in two, so each button now does what the gamepad's does
in Prey, and Prey's prompts name the button to press:

| Frame | Gameplay | Game menus | VR Options |
|---|---|---|---|
| Right A / B | jump / crouch | confirm / back | activate / close |
| Right X | — | Prey's X action (Equip...) | — |
| Right Y | — (with both grips: recenter) | Prey's Y action, on release | — |
| Right Menu | tap pause, hold VR Options | same | — |
| Left View | the TranScribe (`xi_back`) | — | — |
| Left D-pad | — | navigate | navigate / adjust |
| Bumpers | unbound (user's decision) | | |

The Frame's set is one set, suggested under both profile names, newest first. A runtime
refuses a name it doesn't know, and each refusal is logged:
`result=failed step=bindings profile=frame path=... code=...`. Each acceptance is
logged as `result=0 detail=bindings profile=frame path=...`, replacing `set=...`.

**Fixes for every controller:**
- **Recenter is Y on either hand + both grips, in either order.** A grip squeezed while
  Y is held starts nothing. That is a new `chord` input on the use button, separate
  from `busy`: busy releases a hold already under way, and a Y press must not drop a
  carried body. Grips first still recenters, but the first grip still uses or reloads.
  Documented.
- **Y in game menus acts on release.** Holding both grips at any point during the press
  spoils it (`input::ReleaseTap`). The game menus' tabs now use the same type.
- **VR Options tabs act on release**, through the same `ReleaseTap`. Both grips change
  nothing. A grip let go as the panel arms is no tab.
- **Game menus navigate with `TrackingFrame::navigate`**: the right stick plus the
  Frame's D-pad. On Touch and Index that is the right stick alone, as before.
- **Hysteresis** (`input::Pressed`): the trigger presses at 0.5 and releases below 0.4;
  the grip presses at 0.55 and releases below 0.45. The trigger's float value is
  unchanged for the fire axis. Hold frames (`LocateHeldPointer`) keep their plain 0.5,
  because there it only colours the laser.
- **The face-button guards share one helper.** Holsters, psi, medkit and psychoscope
  each refused to act while "the thumb is on a face button". That meant right A/B or
  left X/Y read through `menuAccept`/`menuCancel`. They now use
  `FaceButtonHeld(hand)`: A, B, X, Y or View, whichever that hand has.
- **The controls card** reads "Stick / D-pad: navigate, Y + grips: reset view, Hold
  Menu: VR options".

## Phase 1: named actions, grab on the left trigger (2026-10-17)

After the phase 0 headset test, the user asked for the left hand's grab on the left
trigger rather than its grip, on every controller, and chose that psychic targeting
(opt-in) **shares** the left trigger rather than moving.

**Every action is named for what it does, in three sets** (`preyvr/ControllerProfiles.h`).
Each set is one page of SteamVR's binding UI, which is the rebinding route; the user
ruled out an in-mod one.

| Set (label) | Actions |
|---|---|
| `common` (Hands and System) | `grip_pose`, `aim_pose`; `trigger`, `squeeze` (each hand as such: the laser's click, pages and tabs, foregrip, holsters, medkit slot, psychoscope, the recenter chord); `feedback`; `pause` (hold: VR Options); `recenter` (with both grips) |
| `gameplay` (Gameplay) | `move`, `turn`, `fire`, `grab`, `reload` (hold: holster), `jump`, `crouch`, `inventory` (TranScribe), `weapon_wheel` |
| `menus` (Menus) | `navigate` (+ `navigate_up/down/left/right`, the Frame's D-pad), `scroll`, `confirm`, `back`, `secondary` / `tertiary` (Prey's X / Y), `exit` (the Frame's View) |

Default bindings, on every controller:
- Shared: left stick move / scroll, right stick turn / navigate, right trigger fire,
  **left trigger grab**, right grip reload, right A jump / select, right B crouch / back,
  right stick click for the wheel.
- Touch: X is the TranScribe in play and Prey's X in menus, Y is Prey's Y and recenter,
  and pause is the left menu button.
- Index: as Touch, with left A/B for X/Y and the left stick's click for pause.
- Steam Frame: as in phase 0, plus View is `exit` in menus. View posts the gamepad's
  Back (`MenuAction::Exit`), Prey's `menu_exit`, so View both opens and closes the
  TranScribe.

**All three sets are synced every frame; the plan said "by context", and that changed.**
Syncing only the current context's set would hide buttons held across a menu opening
or closing from the existing rules that make them be let go first:
- `MoveLane`'s `blocked[]` marks a button that is down while a menu is open, so it
  cannot act when play resumes. With the gameplay set unsynced in menus, the button
  would read up throughout, and a held A would jump the moment the menu closed.

So the consumers keep their context gates, unchanged. Sets are equal priority, and a
button bound in two sets (A: `jump` and `confirm`) reaches both actions. The test's rule
is one action per button **per set**.

**The published state** (`XrInput.h`):
- `ControllerState` is a hand as such: poses, trigger, grip, its own stick (diagnostics
  and the laser's push and pull) and `thumbButton` (any thumb button held, for the
  face-button guards).
- The named actions are hand-neutral: `TrackingFrame::play` / `menu` / `system`.
- `MoveLane` reads `move`, `turn`, `fire`, `grab`, `reload` and the buttons;
  `VrOptionsRuntime` and the menu router read `menu` and `system.pause`.

**Grab on the trigger** (`InteractionUse`):
- The use button's inputs are now `leftPress` (grab) and `rightPress` (reload).
- The left hand's busy list drops the foregrip region and the psychoscope zone unless
  the grip is squeezed too: they are the grip's gestures, and still win if grab is
  rebound to the grip.
- The medkit zone (its trigger is the slot's) and a held foregrip still stop a grab.

**Psi shares grab**: `ButtonInput::psi` (psychic targeting on). A grab press with nothing
to grab becomes `Owner::Psi` for as long as it is held, and `PsiMedkit`'s trigger reads
`PsiOwnsGrab()` instead of the raw trigger. With a target, or while carrying, the press
grabs. A press during the reload's guard frames is neither. The medkit slot still reads
the raw left trigger.

**Settings text**: the psi help says "with nothing to grab, hold the left trigger"; the carry
setting is "Carry", choices "press to toggle" / "hold to carry".

**Tests** (74/74):
- `controller_profiles`: one action per role, in order, in its set; names valid for
  OpenXR and unique; every binding's path of its action's kind (pose, `/value`,
  `/thumbstick`, `/click`, haptic); every action on one button; **a button carries one
  action per set**; grab on the left trigger; the Frame's View as `exit`.
- `interaction_use`: psi shares the press (nothing to grab, a target arriving later,
  letting go, busy, off, carrying, the reload guard).
- `menu_navigator`: exit on a fresh press, not the View still down from opening the
  TranScribe; `MenuAction::Exit` is the gamepad's Back.
- `psi_medkit_runtime` and `vr_options_runtime`: re-pointed at `PsiOwnsGrab` and the
  named actions.

Breaking any of five rules makes its test fail (checked): grab back on the grip, two
menu actions on one button, a float action on a click, psi taking a press under the
reload guard, and View not closing a menu.

**Not checked offline**: SteamVR's binding UI with three sets, and xr-sim with more than
one action set. xr-sim's source is not on this machine.

## Phase 3: fingers follow the controller, and a Controls tab (2026-10-17)

The last two plan items: "Individual finger control support", and a controls list
made from what the runtime actually binds.

**Fingers.**
- **The seam was already there.** `AnimIkTakeover`'s `ApplyRelaxedFingers` writes
  every finger joint of a free hand (no weapon, or the left hand off the
  foregrip) from `handpose::ShapeRelative` (flexion scale and closure). It used
  one relaxed pose, and a closure only around a carried object.
- **It is now per finger:** `handpose::ShapeFromController(trigger, indexTouch,
  squeeze, thumbTouch, relaxed)`.
  - **Thumb:** on a button or stick it curls down (closure 0.5); lifted, it
    stands up (flexion 0.3).
  - **Index:** off the trigger it points (flexion 0.25); on it, it rests curled
    (0.2) and closes with the trigger's travel.
  - **Middle, ring, pinky:** close with the grip's travel.
- A carried object still closes the hand: the larger closure wins.
- Each side eases over about 55 ms, so a touch sensor's edge is a movement, not a
  jump.
- The numbers are tuned by eye against the rig's flexion axes and want a headset
  pass.
- **Two new common actions** (`Kind::touch`):
  - `thumb_touch`: Touch's X/Y/A/B, stick and thumbrest; Index's A/B, stick and
    trackpad; the Frame's A/B/X/Y, Menu, stick, D-pad and View.
  - `index_touch`: `trigger/touch` on all three.
  - `ControllerState` gains `thumbTouch` and `indexTouch`.
- **VR Options, Hands: "Fingers follow the controller"** (`finger_curl`, default
  on; `SetAnimIkFingerCurl`). Off is exactly the old relaxed pose.

**The Controls tab.**
- **Reading the bindings.** On each interaction-profile event, `XrInput` asks the
  runtime what every action is bound to (`xrEnumerateBoundSourcesForAction`) and
  what each source is called (`xrGetInputSourceLocalizedName`, user path +
  component: "Right Hand A Button" and the like). It logs
  `detail=bound action=... sources="..."` and keeps the result
  (`XrInputBoundControls`).
- **The tab.** VR Options gains a ninth tab, CONTROLS, before EXPERIMENTAL.
  - It lists play, menus and any time, each action beside its buttons
    (`VrOptionsControlRows`), plus the gestures that are not one button
    (two-hand aim, tabs, recenter).
  - An optional action nothing binds is left out; a required one shows "Not
    bound".
  - It ends with where to rebind.
- **It follows the runtime.** It shows the controller the runtime picked and any
  rebinding in SteamVR, not the mod's suggestions.
- **It is read only:** no control but the tabs, Back and the scrollbar, so the
  trigger anywhere on it grabs the panel.

**Tests** (76/76):
- `hand_pose`: every joint's finger, and each finger from its own input,
  including non-finite and over-range values.
- `controller_profiles`: touch paths of the touch kind, and both fingers' touch on
  both hands of every controller.
- `vr_options_contracts`: nine tabs, CONTROLS holding no setting.
- `vr_options_ui`:
  - the Controls tab read only, waiting and with rows, a long list scrolling;
  - the experimental tab last;
  - the A-off-a-control check, which had parked the laser where the new setting
    row now is, so it now parks it in the names column and checks the premise.
- `vr_options_runtime`: the rows, by section, an optional unbound action left out,

## B leaving the inventory no longer crouches (2026-10-17, package PreyVR-10)

Right B is Back in menus and crouch in play, and backing out of the inventory with
B crouched. The action lanes already ignored a button held while a menu was up,
but each render the main thread posts the queued Back (the inventory closes),
samples the menu state (closed) and only then runs the lanes
(`CameraEditHook.cpp`, `DrainQueuedInput` → `DrainQueuedHudCalls` →
`UpdateTurnAndFireLanes`). So the lanes first saw B on a frame that already read
as gameplay, and posted `xi_b` (`sneak`).

Now the frame a menu closes still counts as the menu's (`input::PlayResume`,
`preyvr/ReleaseGate.h`): a button down then waits for its release. It applies to
every action slot (A confirm then jump, Y, the D-pad, ...), the use button's
arming, the Y tap/hold, and the fire trigger, whose release wait could be cleared
on a menu frame and so had the same race. Test: `release_gate`; `ctest` 77/77.

Unproven alternative: Prey itself routing the posted `xi_b` to `player`'s `sneak`
as the inventory closes. If B still crouches, run `move.act` before and after:
`crouch=... sent=` unchanged means it is Prey's, not the lane's.

Headset checklist (worn 10-17, verified):
1. Open the inventory, back out with B: no crouch. Hold B after backing out: still
   no crouch; let go and press again: crouch.
2. Back out of a dialog with B, and confirm a menu item with A: no crouch, no jump.
3. In play, B and A act at once as before.
